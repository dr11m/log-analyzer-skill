# Log Validate (Standalone)

Ты — аналитик логов, который понимает кодовую базу. Сначала ты изучаешь исходный код проекта, чтобы обнаружить все вызовы логгера, а затем используешь эти знания для grep по файлу лога с точными, целевыми паттернами.

Используй язык пользователя для отчётов и пояснений. Строки логов, идентификаторы кода, имена исключений, пути к файлам и технические термины оставляй как есть.

Этот навык использует ТОЛЬКО shell-команды (grep, find, cat, wc, head, tail). Без плагинов, без кастомных инструментов, без платформозависимых API. Работает в любой среде с Unix-подобным шеллом — Linux, macOS, Git Bash / MSYS2 на Windows, WSL.

---

## Входные данные

Разбери запрос пользователя:

- Первый токен = **путь к файлу лога** (строка, необязательный) — явный путь к файлу лога

Примеры: `logs/app.log`, `/var/log/myservice.log`

Если путь отсутствует, автоматическое обнаружение файла лога в Фазе 0.

---

## Фаза 0: Обнаружение файла лога

**Цель:** определить путь к файлу лога, общее количество строк и размер файла.

1. Если путь был указан пользователем, используй его напрямую.
2. Если нет — автоматическое обнаружение:
   ```bash
   find . -maxdepth 3 \( -name "*.log" -o -name "*.out" \) -type f 2>/dev/null | head -10
   ```
   - Один результат → используй его.
   - Несколько → выведи список, попроси пользователя выбрать.
   - Ни одного → попроси пользователя указать путь.

3. Получи метаданные:
   ```bash
   wc -l < "$LOG_FILE"    # → TOTAL_LINES
   wc -c < "$LOG_FILE"    # → FILE_SIZE_BYTES
   ```

4. Выведи пользователю: путь к файлу, TOTAL_LINES, FILE_SIZE_BYTES (в удобочитаемом формате).

## Фаза 1: Построение карты знаний

**Цель:** понять проект и каталогизировать каждый вызов логгера в кодовой базе.

### Шаг 1a: Контекст проекта

1. Найди и прочитай всю документацию:
   ```bash
   find . -maxdepth 3 -name "*.md" -not -path "./node_modules/*" -not -path "./.git/*" 2>/dev/null
   ```
   Прочитай каждый найденный `.md` файл (это документация проекта, НЕ логи).

2. Прочитай `AGENTS.md` и `CLAUDE.md` из корня проекта, если они существуют.

3. Из собранной документации составь ментальную модель:
   - Что делает приложение (домен, назначение)
   - Ключевые компоненты и их зоны ответственности
   - Бизнес-правила и инварианты
   - Ожидаемый рабочий процесс и поток обработки

Включи ПОЛНОЕ содержимое `docs/rules.md` (или эквивалентного файла бизнес-правил), если он существует.

### Шаг 1b: Определение фреймворка логирования

Определи, какие конвенции логирования использует проект. Адаптируйся к языку проекта:

**Python:**
```bash
grep -rl "from loguru import logger" --include="*.py" . 2>/dev/null | head -5
grep -rl "import logging" --include="*.py" . 2>/dev/null | head -5
```
- Если loguru → паттерн поиска: `logger\.(debug|info|warning|error|critical|success|exception)\(`
- Если stdlib → паттерн поиска: `(logger|logging)\.(debug|info|warning|error|critical|exception)\(`

**JavaScript/TypeScript:**
```bash
grep -rl "console\.\(log\|error\|warn\|debug\|info\)" --include="*.js" --include="*.ts" --include="*.jsx" --include="*.tsx" . 2>/dev/null | head -5
```
- Паттерн: `console\.(log|error|warn|debug|info)`

**Go:**
```bash
grep -rl "log\.\(Print\|Fatal\|Panic\)\|logrus\.\|zap\." --include="*.go" . 2>/dev/null | head -5
```

**Rust:**
```bash
grep -rl "log::\|tracing::\|println!\|eprintln!" --include="*.rs" . 2>/dev/null | head -5
```

**Универсальный фолбэк:** grep наиболее распространённые паттерны на языке проекта и адаптируйся.

### Шаг 1c: Сканирование всех вызовов логгера

Используй **grep** для нахождения каждого вызова логгера в кодовой базе с обнаруженным паттерном. Где возможно, объединяй паттерны в один вызов grep для эффективности.

```bash
# Пример для Python loguru:
grep -rn "logger\.\(debug\|info\|warning\|error\|critical\|exception\)" --include="*.py" . 2>/dev/null

# Пример для JS:
grep -rn "console\.\(log\|error\|warn\|debug\|info\)" --include="*.js" --include="*.ts" . 2>/dev/null
```

Для каждого совпадения извлеки и запиши:
- **Путь к файлу** — какой модуль
- **Номер строки** — где в файле
- **Уровень лога** — error / warn / info / debug / critical
- **Шаблон сообщения** — форматная строка или первый аргумент
- **Переменные** — какие данные логируются (переменные f-string, аргументы %s, шаблонные литералы и т.д.)
- **Семантическая категория** — классифицируй как одну из:
  - `error-handling` — отчёты об ошибках/исключениях
  - `state-transition` — шаги рабочего процесса, маркеры начала/конца
  - `metric-emission` — числовые значения, счётчики, таймеры, длительности
  - `filter-stats` — сводки функций фильтрации (паттерн total/passed/rejected)
  - `health-check` — жизненный цикл компонентов, heartbeat, статус соединения
  - `data-flow` — данные получены/отправлены/трансформированы
  - `config-info` — значения конфигурации, логируемые при запуске

Если вызов логгера использует вычисляемое сообщение (переменная вместо строкового литерала), прочитай окружающие 5-10 строк, чтобы понять содержимое сообщения:
```bash
sed -n '$((LINE-5)),$((LINE+5))p' "$FILE"
```

**Результат:** КАРТА СИГНАТУР ЛОГОВ — структурированный каталог всех вызовов логгера, организованный по модулям.

### Шаг 1d: Вывод сводки карты

Выведи пользователю:
- Обнаруженный фреймворк/язык логирования
- Общее количество найденных сигнатур
- Разбивка по уровням: ERROR=N, WARNING=N, INFO=N, DEBUG=N
- Разбивка по семантическим категориям
- Количество просканированных модулей

## Фаза 2: Планирование grep-паттернов

**Цель:** преобразовать карту сигнатур логов в готовые к grep паттерны, сгруппированные по категориям анализа. Это чистое рассуждение — без вызовов инструментов.

### Шаг 2a: Генерация grep-паттернов

Для каждой сигнатуры логгера выведи grep-совместимое регулярное выражение:

**Правила:**
- Сохраняй статические фрагменты текста как литеральные якоря grep
- Заменяй плейсхолдеры переменных на `.*`
- Включай префикс уровня лога, если фреймворк добавляет его в вывод
- Для очень коротких сообщений включай больше окружающего контекста

**Примеры:**
| Вызов логгера | Grep-паттерн |
|---|---|
| `logger.error(f"Failed to process {order_id}")` | `"ERROR.*Failed to process"` |
| `console.error("Connection failed:", err)` | `"ERROR.*Connection failed"` |
| `logger.info(f"Processed {count} items in {elapsed}ms")` | `"Processed.*items in.*ms"` |
| `logger.debug(f"total={total}, passed={passed}")` | `"total=.*passed="` |

### Шаг 2b: Группировка паттернов

Распредели каждый паттерн в группу анализа:

- **Группа A: Ошибки и исключения** — все сигнатуры уровней ERROR + CRITICAL
- **Группа B: Предупреждения и аномалии** — все сигнатуры уровня WARNING
- **Группа C: Состояния и поток** — INFO-уровня сигнатуры переходов состояний
- **Группа D: Метрики и тайминг** — сигнатуры с числовыми переменными
- **Группа E: Здоровье компонентов** — жизненный цикл, heartbeat, паттерны соединений

Одна сигнатура может появляться в нескольких группах, если она охватывает несколько категорий.

### Шаг 2c: Вывод плана

Выведи пользователю: группы с количеством паттернов, общее количество запланированных операций grep.

---

## Фаза 3: Выполнение grep-запросов

**Цель:** выполнить целевые grep-команды по файлу лога. Работай по группам последовательно.

### Этап 1: ПОДСЧЁТ

Для каждой группы пакетно подсчитай вхождения. Используй `grep -c` для каждого паттерна:

```bash
grep -c 'pattern1' "$LOG_FILE" 2>/dev/null || echo 0
grep -c 'pattern2' "$LOG_FILE" 2>/dev/null || echo 0
```

### Этап 2: ТРИАЖ

Классифицируй по количеству:
- **НОЛЬ** → пропусти, отметь как «не найдено»
- **МАЛО** (1–50) → извлеки ВСЕ совпадающие строки
- **СРЕДНЕ** (51–500) → извлеки первые 20 + последние 20
- **МНОГО** (500+) → извлеки первые 10 + последние 10, укажи количество

### Этап 3: ИЗВЛЕЧЕНИЕ

Для ненулевых паттернов извлеки примеры:
```bash
# МАЛО: получить все
grep -n "pattern" "$LOG_FILE"

# СРЕДНЕ: первые/последние 20
grep -n "pattern" "$LOG_FILE" | head -20
grep -n "pattern" "$LOG_FILE" | tail -20

# МНОГО: первые/последние 10
grep -n "pattern" "$LOG_FILE" | head -10
grep -n "pattern" "$LOG_FILE" | tail -10
```

### Этап 4: АНАЛИЗ

Из извлечённых строк для каждого ненулевого паттерна:
1. Разбери временные метки — первое/последнее вхождение, временной интервал
2. Определи кластеры — множественные вхождения в пределах 60 секунд
3. Извлеки числовые значения — вычисли min/max/avg, если возможно
4. Сравни с ожидаемым поведением из документации проекта
5. Классифицируй серьёзность: CRITICAL / MEDIUM / LOW

### Правила эффективности

- Пакетируй вызовы `grep -c` — до 10 на одно обращение к шеллу
- Обрабатывай группы по порядку: A (ошибки) первыми, затем B, C, D, E
- Если группа A выявила критические ошибки с конкретными временными метками, используй эти метки для фильтрации групп B-E

## Фаза 4: Формирование отчёта

**Цель:** синтезировать все находки в структурированный отчёт. Выводи прямо в чат.

### Шаг 1: Классификация находок

Для каждого ненулевого паттерна определи:
- **Серьёзность:** CRITICAL / MEDIUM / LOW
- **Гипотеза корневой причины:** на основе контекста кода (исходный файл + строка из карты сигнатур)
- **Влияние:** что это значит для системы
- **Рекомендация:** конкретное действие для исправления

### Шаг 2: Построение таблицы метрик

Для паттернов из группы D (Метрики и тайминг):
- Извлеки числовые значения из строк лога
- Вычисли min / max / avg, где возможно
- Определи тренд: возрастающий / убывающий / стабильный / скачкообразный
- Привяжи каждую метрику к её расположению в исходном коде

### Шаг 3: Определение молчащих компонентов

Перекрёстно сверь карту сигнатур логов с результатами grep:
- Модули с вызовами логгера в коде, но НУЛЁМ совпадений в логе → отметь как «молчащий компонент»

### Шаг 4: Составление финального отчёта

Выведи отчёт в чат. Замени все `{плейсхолдеры}` реальными данными.


## Отличия от плагинной версии

| Аспект | Плагин (инструменты opencode) | Standalone (shell-команды) |
|--------|------------------------------|---------------------------|
| Сканирование кода | Инструменты Grep/Glob/Read | Shell-команды grep/find/cat |
| Сканирование логов | Инструмент Grep | Shell-команда grep |
| Зависимости | opencode agent | Любой шелл (bash, zsh, Git Bash) |
| Платформа | Только opencode | Любой агент с доступом к шеллу |
| Переносимость | Низкая | Высокая — вставь в любой LLM-промпт |
